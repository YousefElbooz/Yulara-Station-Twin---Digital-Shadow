# Yulara Station Twin: technical guide, file by file

What every file in this repository does, how the parts connect, and, in depth, how the **physical model** and the **digital shadow (twin)** work. Written 2026-11-21 against the code as it is now. Numbers quoted here come from the generated reports in `docs/`.

---

## 1. The system in one picture

```
 OFFLINE PIPELINE (scripts/, run once, in order)                    ONLINE (backend/ + frontend/)
 ───────────────────────────────────────────────                    ─────────────────────────────
 data/raw/5-Site_DG-PV1-…csv ──► 1  clean_station_data ──► station_5min.parquet ─┐
 ERA5 (CDS) ──► download_era5_yulara ──► era5_hourly_site_utc.csv               │
            1b correct_ghi_sensor ──► ghi_corrected_5min.parquet                 │
            1c build_model_weather ─► weather_model_5min.parquet (+ src tags) ───┤
            3  simulate_physics ────► physics_5min.parquet (p_expected_kw)       │   TwinRunner thread
            4  calibrate_physics ───► calibration.yaml + p_expected_cal_kw       ├─► SimClock ─► Source.get(t)
            5  compute_health ──────► health_daily.parquet, health_events.csv    │     └► TwinEngine.step(t)
            7  train_friend_models ─► models_store/friend_v1/*                   │          ├ pv_chain.simulate
               predict_ml_models ───► ml_predictions_5min.parquet ───────────────┘          ├ status + alarms
                                                                                            └ Store (SQLite)
                                                    FastAPI (backend/api/app.py) reads SQLite + parquet
                                                                  │  /api/now /series /scene /alarms /whatif …
                                                    React + Three.js website (frontend/) ◄─┘
```

**The idea in one sentence:** the physics says what the plant *should* produce, the plant's meter says what it *did* produce, the ML models say what it *will* produce, and the twin turns the gaps between them into named causes (held back, outage, fault, soiling) and alarms with recommendations for a person.

**Why a "shadow" and not a "twin":** data flows automatically from the plant to the model, but nothing flows back automatically. The output is recommendations to a person (Kritzinger et al. 2018).

## 3. Configuration (`config/`)

| File | Role |
|---|---|
| `station.yaml` | The plant as the model sees it: location (−25.2427, 130.9820, 492 m, `Australia/Darwin`), array (3,360 × Jinko JKM315PP-72, 1,058.4 kW DC, tilt 15°, azimuth 0° = north, 15 rows), module datasheet (γ −0.40 %/°C, NOCT 45 °C, 16.23 %), inverter (SMA STP 25000TL-30, euro η 0.981, **count 42 and AC 1,050 kW calculated, not published**). Sources and confidence for each value: `docs/station_facts.md`. |
| `physics.yaml` | Which pvlib models make up the chain (Erbs, Perez, physical IAM, SAPM open rack glass/polymer), the timestamp convention (`end`), albedo 0.25 (**assumed**), version-0 DC loss 14 %, and the clear-day rules used only to validate. |
| `calibration.yaml` | Written by `calibrate_physics.py`: calibration v1, fitted 2020–2024, DC loss **10.21 %**, scale 1.0441 vs version 0, 47,401 samples. It also records what was *not* calibrated and why. |
| `data.yaml` | Cleaning rules: raw-to-canonical column names, the 3 dropped channels and their reasons, sentinel threshold, valid range per channel, stuck-value rule, GHI-correction settings (`constant`, from 2024-04-01), and the ERA5 fallback. |
| `twin.yaml` | `health`: unlimited-moment definition, PR smoothing, soiling / fault / outage / equipment-heat thresholds. `runtime`: the SQLite path, clock mode, data window, tick, demo profile, step-status thresholds and the alarm catalogue (message, recommendation, debounce steps). |

**Design rule:** no threshold or physical constant is hard-coded in the logic. Change the YAML, re-run the scripts, and the reports regenerate.

## 4. The offline pipeline (`scripts/`), in run order

### 4.1 `clean_station_data.py` (step 1)

Turns the DKASC file (1,018,216 rows, ACST clock, raw units) into `data/clean/station_5min.parquet`.

**What it does:**
1. Reads only the 11 mapped channels and renames them (`data.yaml → columns`).
2. Drops duplicate timestamps.
3. Converts the clock: the file is local **ACST** (UTC + 9:30, no daylight saving), and everything is stored in **UTC**. This was verified in the data: the GHI-weighted centre of each day sits within 0–5 min of pvlib solar noon in ACST.
4. Converts sentinels (< −1000, e.g. −9 × 10⁹) and out-of-range values to missing.
5. Builds a **regular 5-min grid**: the missing steps are added back (21,755 of them), giving **1,039,971 rows**.
6. Adds the sun elevation and five flags:
   - `flag_gap`: the step was not in the file.
   - `flag_missing_power`.
   - `flag_night`: sun below 0°.
   - `flag_bad_sensor`: any value out of range.
   - `flag_stuck_power`: power repeats within 0.5 kW for ≥ 6 steps in daylight above 5 kW.
7. Writes `docs/quality_report_station.md`.

**Why flags instead of deleting:** every downstream step can choose what to exclude, and nothing is filled without saying so.

### 4.2 `correct_ghi_sensor.py` (step 1b)

**The finding:** the site GHI sensor reads **+14.3 %** from 1 April 2024. The ratio site ÷ ERA5 jumped from 0.988 in March to 1.169 in April. The jump has the same size in every calendar month (1.140 in 2024, 1.142 in 2025, ±0.031), and the tilted `Pyranometer_1` shows no jump.

**The method (`constant`):**
- Compare each month after the change with the **same calendar month before it**. ERA5 is seasonally lower than the site in winter even before 2024, so comparing against the all-year mean would be wrong.
- Apply one factor, **× 0.875**, to the whole period after the change.
- The raw `ghi_wm2` is kept untouched.

**Output:** `ghi_corrected_5min.parquet` and `docs/ghi_sensor_correction.md`.

**Status:** this is an **assumption**: no DKASC note confirms that the sensor was changed. It can be reversed with `method: monthly`, or by removing the step.

### 4.3 `build_model_weather.py` (step 1c)

Builds the weather the physics will actually use, one value per 5-min step, with its source.

- **GHI:** the corrected site GHI; when the sensor is offline, ERA5 GHI × the site/ERA5 ratio for the same calendar month (0.98–1.10).
- **Temperature:** the site sensor, else ERA5 − 0.11 °C.
- **Wind:** the site sensor, else ERA5 × 0.526 (the site sensor is lower than 10 m).

**How the matching factors were found:** fitted on daylight hours before April 2024. The ERA5 hourly values are first placed at the centre of their hour, then interpolated to the middle of each 5-min step.

**Source tags:** `src_ghi`, `src_temp` and `src_wind` take one of the values `station`, `station_corrected` or `era5`. In daylight 2016–2026, **51,677** GHI steps were filled from ERA5, and none was left empty.

**Rule:** calibration and validation never use ERA5-filled steps. They exist so the twin can still compute something while the sensors are off, and they are labelled.

### 4.4 `download_era5_yulara.py`

Downloads ERA5 single levels from the Copernicus CDS:
- 14 variables (radiation, clear-sky radiation, direct radiation, cloud layers, 2 m temperature and dew point, 10 m wind u/v, pressure, water vapour, precipitation).
- A ±0.5° box around the site, one file per month, 4 parallel workers, with retries.
- Output: `data/era5/era5_hourly_site_utc.csv` with "hour-ending" stamps. Accumulated J/m² are converted to W/m² by ÷ 3600, and K to °C.

The settings are identical to the ML team's notebook, so the models see the same inputs. It needs `CDSAPI_KEY` in `.env`.

### 4.5 `simulate_physics.py` (step 3)

Runs `backend/physics/pv_chain.simulate()` over the whole history (version 0, DC loss 14 %) and writes `physics_5min.parquet`: zenith, azimuth, DNI, DHI, POA global and effective, AOI, cell temperature, P_dc, P_expected and Haurwitz clear-sky GHI.

It then validates on **clear days**, selected by three rules:
- ≥ 95 % daylight coverage;
- daily irradiation within 0.90–1.15 of Haurwitz clear sky;
- Stein variability index ≤ 1.10.

**Result:** 867 clear days. This step found the midday holding back: measured ÷ expected is 0.14 at noon in winter and 0.47 at noon in summer (`docs/physics_validation.md`).

### 4.6 `calibrate_physics.py` (step 4)

Detailed in §5.3. It writes `calibration.yaml`, adds `p_expected_cal_kw` to the physics parquet, and writes `docs/calibration_report.md`.

### 4.7 `compute_health.py` (step 5)

Runs `backend/health/indicators.py` over 2016–2026 and writes:
- `health_daily.parquet`: one row per local day;
- `health_events.csv`: outage, soiling and fault events;
- `docs/health_report.md`: the yearly energy split (physics allows / measured / health loss / limit loss / outage loss) and a monthly PR table.

The twin starts from this history, so its rolling indicators are warm on the first day.

### 4.8 `train_friend_models.py` and `predict_ml_models.py` (step 7)

**`train_friend_models.py`:** a faithful port of the ML team's notebook (`PV_Forecasting_Analysis_Suite_ERA5.ipynb`): same features, the same chronological 70/15/15 split (682,414 / 146,232 / 146,232), the same seeds and hyper-parameters. It trains:
- Ridge, Random Forest, XGBoost and LightGBM;
- DP-PINN (day-ahead and nowcast);
- LightGBM nowcast;
- a stacking meta-model.

Two fixes versus the notebook: the day-ahead PINN scaler is saved too, and the nowcast checkpoint stores the right feature count (76). Progress is written to `data/training/progress.json`.

**`predict_ml_models.py`:**
- Runs every model **through its adapter** (§7) and proves the adapters reproduce the training run (difference 0.0000).
- Writes `ml_predictions_5min.parquet`, one column per model, from 2022-10-30.
- Compares all models with the calibrated physics on 2025, both "all daylight" and "unlimited moments only" (`docs/model_comparison_2025.md`).

**Known limitation (honest):** the day-ahead track uses **ERA5 at the target hour**, which acts as a perfect weather forecast, and the day-ahead PINN base reads it too (`train_friend_models.py:631`). Day-ahead scores are therefore an upper bound until the forecast origin is fixed and an NWP forecast replaces ERA5.

### 4.9 `run_twin.py`

`build(args)` assembles the twin: it loads the configs, the clock, the health history (closed days before the start), daily rain from ERA5, the `Store`, the precomputed ML predictions, the `TwinEngine` and the source (`HistorySource`, or `LiveWeatherSource` in live-weather mode). The twin always starts at **local midnight** of its first day, so "today" is complete.

It is used in three ways:
- by `TwinRunner` (inside the API);
- from the command line, as a live loop: `--mode mirror|speed`;
- `--fast --start … --until …`: processes a period as fast as possible and prints every alarm. This is the regression test of the twin's logic.

## 5. The physical model, in depth (`backend/physics/pv_chain.py`)

`simulate(weather, station, physics, calibration=None)` takes a frame of `ghi_wm2`, `t_air_c` and `wind_ms` on a UTC index, and returns every intermediate quantity. **The same function** serves the history run, the calibration, the live twin (one row per step) and the what-if endpoint, so there is only one physics in the project.

### 5.1 The chain, step by step

**0. Sun position (pvlib SPA)**
- Computed at the **middle of each 5-min interval**: stamps label the *end* of the interval, so the sun is evaluated at t − 2.5 min.
- Gives the zenith Z, apparent zenith Z′ (with refraction) and azimuth φₛ. Night (Z′ ≥ 90°) forces GHI = 0.

**1. Decomposition, GHI → DNI + DHI (Erbs 1982).** The station measures only GHI, so it must be split. With the clearness index kt = GHI / (E₀ · cos Z):

```
diffuse fraction  DF = 1 − 0.09·kt                                           kt ≤ 0.22
                     = 0.9511 − 0.1604·kt + 4.388·kt² − 16.638·kt³ + 12.336·kt⁴   0.22 < kt ≤ 0.80
                     = 0.165                                                 kt > 0.80
DHI = DF · GHI          DNI = (GHI − DHI) / cos Z
```

Missing GHI stays missing: the code re-applies the NaN mask after Erbs, because Erbs plus `fillna` would otherwise turn "unknown" into 0.

**2. Transposition onto the panel plane (Perez 1990).** The panels are tilted β = 15° and face north (pvlib azimuth 0°). With AOI the angle between the sun and the panel normal:

```
cos AOI  = cos Z′·cos β + sin Z′·sin β·cos(φₛ − φₚ)
POA_beam = DNI · max(cos AOI, 0)
POA_sky  = DHI · [ (1 − F1)·(1 + cos β)/2 + F1·a/b + F2·sin β ]   (Perez anisotropic sky)
POA_gnd  = GHI · ρ · (1 − cos β)/2                                (ρ = albedo 0.25, assumed: red sand)
```

- F1 (circumsolar) and F2 (horizon brightening) come from Perez's coefficient table, which is indexed by sky clearness ε and brightness Δ.
- Δ uses the relative airmass and the extra-terrestrial irradiance.
- Perez is more accurate than an isotropic sky because, on clear days, much of the diffuse light comes from around the sun.

**3. Reflection loss (IAM, "physical" Fresnel/Snell model)**
- Glass reflects more light at steep angles. It is applied **to the direct part only**, because diffuse light arrives from all angles and its IAM is close to constant.
- `POA_eff = POA_beam · IAM(AOI) + POA_diffuse`.

**4. Cell temperature (SAPM, open rack, glass/polymer)**

```
T_module = POA · exp(a + b·WS) + T_air          a = −3.56, b = −0.075
T_cell   = T_module + (POA / 1000) · ΔT         ΔT = 3 °C
```

A missing wind value is replaced by 1 m/s (the only default in the chain). Hot cells lose power, which is the next step.

**5. DC power (PVWatts DC) and DC losses**

```
P_dc = (POA_eff / 1000) · P_dc0 · (1 + γ·(T_cell − 25)) · (1 − L)
P_dc0 = 1,058.4 kW,  γ = −0.0040 /°C (datasheet),  L = DC losses
```

**6. Inverter (PVWatts inverter)**

```
ζ = P_dc / P_dc0,inv          P_dc0,inv = P_ac0 / η_nom,  P_ac0 = 1,050 kW (calculated), η_nom = 0.981
η = (η_nom / 0.9637) · (−0.0162·ζ − 0.0059/ζ + 0.9858)
P_ac = min(η · P_dc, P_ac0)   then clipped ≥ 0, and forced to 0 at night
```

The AC limit is never reached: the maximum measured is 916 kW, so there is no inverter clipping in the data.

**7. Clear-sky reference (Haurwitz)**
- `GHI_cs = 1098 · cos Z · exp(−0.057 / cos Z)`.
- Used for the clearness index and for picking clear days. It is not used in the power itself.

**Output columns:** `sun_zenith_deg, sun_azimuth_deg, dni_wm2, dhi_wm2, poa_global_wm2, poa_effective_wm2, aoi_deg, t_cell_c, p_dc_kw, p_expected_kw, ghi_clearsky_wm2` (float32).

### 5.2 Worked example (15 Jul 2023, 12:50 ACST, a clear winter day)

| Quantity | Value |
|---|---|
| Sun elevation / zenith | 43.2° / 46.8° |
| GHI measured / clear-sky | 701 / 689 W/m² → kt ≈ 1.0 (clear) |
| Air temperature → cell temperature | 19.1 °C → 40.9 °C |
| Expected AC (calibrated) | **757 kW** |
| Measured | **462 kW** → status `limited` (< 70 % of expected while expected ≥ 300 kW) |

### 5.3 Calibration (`scripts/calibrate_physics.py`)

**What is fitted:** one number, the plant's real DC loss.

**On which moments:** only moments when the plant is **free to follow the sun** ("unlimited"):
- sun > 10°;
- expected power 50–300 kW (the holding back happens at high midday power);
- no stuck power and no gap;
- GHI from the station, not ERA5;
- ratio measured/expected trimmed to 0.5–1.5 (passing clouds, glitches).

**Training period:** 2020–2024, 47,401 samples. 2025 is held out for the test.

**Estimator:** least squares through the origin of measured on expected (version 0):

```
k = Σ(m·e) / Σ(e²) = 1.0441          L₁ = 1 − k·(1 − L₀) = 1 − 1.0441·0.86 = 10.21 %
```

**Not calibrated, on purpose:**
- the AC limit (never reached);
- γ, because unlimited moments are early or late in the day with cool cells, so the data cannot see the temperature effect.

**The same fit, year by year:**
- The scale falls by **−0.95 %/yr**. Typical crystalline silicon loses 0.5–0.8 %/yr, so this trend is faster than usual.
- 2024 is low (0.968), and 2024 also contains the GHI sensor change.
- This is reported as ageing/dirt, but it is an **assumption**.

**Test on 2025:**

| Evaluation | RMSE | Share of capacity |
|---|---|---|
| Unlimited moments (6,793) | 33.7 kW | 3.18 % of capacity, bias +0.5 kW |
| Same moments, weather filled from ERA5 | 67.7 kW | the cost of losing the site sensors |
| All daylight | 350.6 kW | large on purpose: it includes the holding back, which the physics must not predict |

In 2025 the plant delivered 978 MWh, against 1,950 MWh that the calibrated physics allowed (50 %).

## 6. The digital shadow, in depth (`backend/twin/`, `backend/health/`)

### 6.1 Clock (`clock.py`): "which 5-min step is now?"

| Mode | "Now" is | Used for |
|---|---|---|
| `mirror` | Today's date and local time at Yulara, taken from the latest year that has data (handles 29 Feb) | The default "looks live" mode, at real speed |
| `speed` | A chosen local start + (wall time elapsed × speed factor) | Replay and demos (e.g. ×90) |
| `realtime` | The real UTC now, floored to 5 min | Live-weather mode |

Steps are labelled at the **end** of their 5-min interval, like the station file. `now()` never goes beyond the last step in the data.

### 6.2 Sources (`source.py`, `live_weather.py`): where a step's inputs come from

**`HistorySource`:**
- Loads the cleaned station table, joined with the model weather, from `data_from` onwards.
- `get(t)` returns **one step as a plain dict**: measured power, sensors, model weather with its source tags, and the flags. That is exactly what a live DKASC feed would deliver, so swapping in a live feed later means writing one class with the same `get(t)`.

**`LiveWeatherSource`:**
- Calls Open-Meteo (`/v1/forecast`, 15-min values, every 10 min, no key) and interpolates to 5 min.
- Wind direction is interpolated as a unit vector, so 350° → 10° does not swing through 180°.
- Returns the same dict with `p_ac_kw = None` (no live plant feed).
- The weather is labelled `open-meteo` because these are **weather-model values, not measurements**.

### 6.3 Engine (`engine.py`): one call per 5-min step

`TwinEngine.step(t, row)` does the following, every step:

1. **Day boundary:** if the local date changed, close the previous day (§6.5).
2. **Physics for this moment:** if GHI and temperature exist, run `simulate()` on a one-row frame with the **calibrated** DC loss, giving `expected_kw`, POA and cell temperature. With no weather there is no expected power: *the engine never invents numbers*.
3. **Status:** the first rule that matches wins.

   | Status | Rule |
   |---|---|
   | `night` | sun ≤ 0° |
   | `weather_only` | no measurement, live-weather mode |
   | `offline` | no measurement from the plant |
   | `outage` | expected ≥ 100 kW **and** measured < 5 % of expected |
   | `limited` (held back) | expected ≥ 300 kW **and** measured < 70 % of expected |
   | `healthy` | otherwise |

4. **Weather source:** `era5` if the GHI or temperature came from ERA5.
5. **Save:** the step goes to the store. The ML predictions for `t` are looked up in `PrecomputedPredictions` and stored with it.
6. **Step alarms**, judged only when meaningful:
   - `OFFLINE`: daylight steps only, and only with a plant feed.
   - `OUTAGE`: only while the physics expects ≥ 100 kW, so dawn and dusk neither open nor close it.
   - `WEATHER_SENSORS_OFF`: the weather source is ERA5.
   - `EQUIPMENT_HOT`: a probe is above 75 °C.
7. **Today's buffer:** the step is appended for the end-of-day computation, and the "now" state is saved for the API.

### 6.4 Alarm logic (debouncing)

Each step alarm has a pair of counters: [steps in the condition, steps out of it].
- It **opens after N consecutive steps** in the condition. N = 6 = 30 min, from `twin.yaml`.
- Its start time is back-dated to the first of those N steps.
- It **closes after N consecutive steps** out of the condition.

This stops a single noisy reading from opening or closing an alarm. That is why the real outage of **4 Oct 2025** (the plant stopped at 10:40) opened the OUTAGE alarm at about **11:10**.

Every alarm carries a severity (`info` / `warning` / `critical`), a confidence, a message and a **recommendation** for a person. The shadow never commands the plant.

### 6.5 Closing a day (`_close_day`, `backend/health/indicators.py`)

At each local midnight, the day's 5-min rows become one daily record (`daily_table` + `add_rolling`):

| Quantity | Definition |
|---|---|
| `measured_kwh`, `expected_kwh` | Σ kW / 12 over daylight steps where **both** exist |
| `coverage` | share of daylight steps with both |
| `pr_unlimited` | Σ measured / Σ expected over the day's unlimited moments (needs ≥ 12 of them, i.e. 1 h) |
| `pr_smooth` | 7-day rolling median of `pr_unlimited` |
| `health_kwh` | expected × pr_smooth (capped at 1.1): what the plant could make *in its current condition* |
| `health_loss_kwh` | expected − health: ageing, dirt, broken parts |
| `limit_loss_kwh` | health − measured (≥ 0): energy it could make but did not, i.e. **held back** |
| `soiling_index` | pr_smooth ÷ its highest value in the last 30 days |
| `pr_vs_month` | pr_smooth ÷ the median of the previous 30 days (shifted one day, so it never sees itself) |
| `outage_day` | expected ≥ 2,000 kWh, coverage ≥ 0.8, measured < 5 % of expected. Its gap is booked as `outage_loss_kwh`, not as limiting |

**The daily identity:** physics allows = measured + health loss + limit loss + outage loss.

**The daily alarms:**
- `FAULT`: pr_vs_month < 0.85 for 3 days.
- `SOILING`: soiling_index < 0.95 for 7 days. It has **low** confidence, because soiling cannot be separated from output limiting.

All rolling windows look **only backwards**, so the live twin can append a day and recompute without seeing the future. In live-weather mode no day is closed, because a day with no measurement would be a fake 0 kWh day.

### 6.6 Store (`store.py`): the twin's memory

The store is SQLite in **WAL** mode, so the API reads while the twin writes without locking each other out. It has five tables:

| Table | Content |
|---|---|
| `steps` | every 5-min step |
| `predictions` | the ML forecasts per step |
| `alarms` | open and closed alarms |
| `days` | closed days |
| `state` | `now` and `meta`, as JSON |

- **Reset** empties the tables instead of deleting the file. On Windows the file cannot be deleted while the API has it open.
- The API uses **read-only** connections (`reader()`).

### 6.7 Runner (`runner.py`): keeping the twin alive

`TwinRunner` is a daemon thread inside the API process:
- It calls `run_twin.build()` (heavy imports happen here, off the request path).
- It loops: process every step up to `clock.now()`, commit, then sleep for `tick_seconds` (5 s, or 2 s in fast replay).
- `stop()` sets an event, so a settings change in the website restarts the twin cleanly with a new mode.
- Errors set `status = "error"` and are reported by `/api/health`.

**Design decision:** the twin runs whether or not anyone has the page open, like a real monitoring system.

## 7. ML in the twin (`backend/models/`)

| File | Role |
|---|---|
| `features.py` | The ML team's feature pipeline as one function: 71 day-ahead features, and 76 for nowcast (+ power 5, 10, 15, 30, 60 min ago). Exact timestamp lags, ERA5 interpolated to 5 min, cyclic time. Its index is local ACST; `to_utc()` aligns it with the twin. |
| `adapters.py` | One adapter per trained model, all with the same interface, `predict(table, rows) → kW`. |
| `hub.py` | `PrecomputedPredictions`: in replay, the forecasts for the whole period are computed once by `predict_ml_models.py` and looked up by time. Live, the same keys would come from running the adapters on the latest week. |

**The adapters:**

| Adapter | Models | How it predicts |
|---|---|---|
| `TabularAdapter` | Ridge, RF, XGBoost, LightGBM, LightGBM nowcast | joblib model → `predict(X)` clipped at ≥ 0 |
| `PinnAdapter` | DP-PINN day-ahead and nowcast | rebuilds the network from its checkpoint, scales the inputs, takes a 12-step (1 h) window, adds a correction to a base, output `softplus(base + delta)`, so never negative |
| `StackingAdapter` | Stacking | Ridge meta-model over five members (RF, XGB, LGBM, LGBM-nowcast, PINN-nowcast) |

**`ResidualCNNLSTM`:** the DP-PINN architecture. Conv1d(n → 32) → Conv1d(32 → 48) → LSTM(64) → MLP head → delta.

**The base for each track:**
- Nowcast: the last 5-min power.
- Day-ahead: 0.65 × a simple STC physics term + 0.35 × the same time yesterday.

**The known issue:** the learned η sticks at its upper bound (0.35) and α at −0.001, because the physics term counts efficiency twice and uses horizontal instead of tilted light. The fix is the first step of the plan.

## 8. API (`backend/api/`)

`app.py` (FastAPI). The website only talks to this; it never computes plant physics itself. On start-up, `lifespan` starts a `TwinRunner`:
- in `mirror` by default;
- with `TWIN_PROFILE=demo`, a ×90 replay from 4 Oct 2025 08:15;
- with `TWIN_PROFILE=live-weather`, live weather.

`TWIN_RUN=0` serves the stored state without running the loop.

| Endpoint | Returns |
|---|---|
| `GET /api/health` | API up? twin status, clock, last step, live-weather fetch info |
| `GET /api/now` | latest step, today's measured and expected kWh, open alarms |
| `GET/POST /api/twin/config` | current mode and allowed range. `POST` restarts the twin: live, replay from a local date at a speed, or weather |
| `GET /api/series` | 5-min series: measured, physics, ML forecasts, weather |
| `GET /api/days` | closed days of the running twin |
| `GET /api/alarms` | alarm log |
| `GET /api/health-history` | the 2016–2026 yearly energy split and events from step 5 |
| `GET /api/station` | station facts, calibration and layout, with calculated values marked |
| `GET /api/models` | the 8 models, their track, and test and 2025 scores |
| `GET /api/scene` | everything the 3D view animates: sun position, weather (rain and cloud from ERA5 or Open-Meteo), cell temperature and heat loss, dust index, measured / expected / held-back power, status, equipment temperature, open alarms, layout |
| `POST /api/whatif` | re-runs the calibrated physics for one real day with changed temperature, dust, tilt, azimuth, γ or ageing, and returns baseline vs scenario energy (this feature is no longer shown in the presentation, but the endpoint exists) |

**The other files:**
- `demo_app.py` and `live_weather_app.py` are two tiny entry points that set `TWIN_PROFILE` and import the app. They are used by the launch configs `twin-api-demo` and `twin-api-live-weather`.
- A `sqlite3.OperationalError` raised while the twin restarts becomes **503** "the twin is restarting", not a crash.
- CORS allows only the localhost dev ports. **Deployment must add the public site's origin.**

## 12. Deployment notes (read before publishing)

1. **Data licence:** DKASC allows use with attribution, but needs **consent above 5,000 cells**. The API serves measured power and sensor series, so a public deployment of the full backend is redistribution of the DKASC data. Either get DKASC's permission, or publish only derived results plus ≤ 5,000 cells of measured data.
2. **Secrets:** `.env` (`CDSAPI_KEY`) is used only by `download_era5_yulara.py`. It is never needed at run time and must never be uploaded.
3. **Runtime shape:** the backend is a long-running process: a background thread plus SQLite writes, ≈ 170 MB of parquet, and torch / xgboost / lightgbm / pvlib (torch alone ≈ 700 MB installed). That does **not** fit serverless platforms (Vercel functions: ≈ 250 MB bundle, no background threads, read-only file system except `/tmp`, short timeouts). The **frontend** is a plain static build and fits Vercel perfectly.
4. **CORS / API base:** the frontend uses relative `/api` paths. A deployment must either serve the API under the same domain (a Vercel rewrite to the API host) or set an API base URL, and add the site's origin to CORS.
